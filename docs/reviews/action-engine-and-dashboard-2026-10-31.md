# Action origins and interactive reporting

New actions must originate from a real form or review. The Actions tab is a management inbox: it supports permitted updates, implementation-date extensions, completion, cancellation, restoration and native process progress, but has no standalone creation form or submission route.

The generic API resolves an action's source type from the stored source record. It rejects missing, archived, unsupported, inaccessible or mismatched origins and protects native action workflows from bypass. LIV visit/cycle and probation observation references must belong to their parent source. Existing form creators remain supported. Coaching, ELI, QA Hub, UCO, Digital Learning Walk and Activate+ creators retain their dedicated workflow and provenance.

Earlier actions without a recorded source remain readable and manageable under their existing permissions. They are labelled Origin not recorded, with no invented link or process attribution. Source aliases and human-readable labels are aligned across the inbox, dashboard and export. Administration identifies the earlier unlinked-action theme list as historical.

The action inbox uses mutually exclusive displayed lifecycle states for its counts, including overdue extended actions and records with a completed date. A cancelled action is not reported as completed merely because it retains an earlier completion date. The deleted-history request also ignores responses superseded by a changed year or toggle.

The Actions dashboard applies the UCO dashboard's visual approach: a completion summary, clickable lifecycle and origin breakdowns, priority attention items and a synchronized detail register. Exploration controls preserve the underlying report's permission, academic-year, organisation and date scope. Each action counts once, including shared Activate+ actions; multiple responsible names remain associated with that one row.

The reporting grain is the central action record. A shared Activate+ action counts once for its several responsible people. A QA action group can contain several separate assigned actions; each assignment action counts once, rather than counting the group or multiplying rows during joins.

Source process, record title and date are visible in reporting. Excel uses readable origin names and retains source titles/dates while excluding internal source IDs. Earlier unlinked actions use their created date to determine academic-year membership, matching the inbox/dashboard convention. Native process completion evidence, review visibility, participant access and lifecycle requirements remain distinct.

The audit also identified native metadata that must stay under its source workflow. Generic structural edits, deletion and restoration of linked QA, UCO, ELI and Coaching actions are protected so QA assignments cannot diverge from group metadata and superseded source plans cannot be resurrected. Ordinary completion, cancellation and audited implementation-date extensions remain central where permitted. QA progression observes the actual action-group state; closing the QA review itself does not lock its later improvement actions.

The inbox receives a read-only SourceWorkflowLocked hint only for actions it is already authorised to see. This preserves valid reopening of completed assignments in an open QA group while hiding invalid progress controls for closed groups. Every mutation rechecks the actual source state inside its transaction. Older Coaching actions with null progress now align completed/closed/not_started with central Complete/Cancel/Reopen updates.

Final verification passed all 484 frontend tests and 694 backend tests with no skips, plus the production web build and Release backend compilation. Disposable database regressions cover authoritative origins, forged or inaccessible contexts, native bypasses, structural edit/delete/restore restrictions, valid QA reopening, closed-group locks, Coaching status alignment and retained legacy management. The actual inbox and dashboard components passed desktop/mobile browser checks with dummy data, including origin/state drilldowns, shared responsibilities, pagination, reset, native-source locks, source links, keyboard focus and 390-pixel containment.

Local services were refreshed with database preparation skipped. Live checks confirmed the originless creation request receives HTTP 400, inbox/dashboard/form-data reads succeed, Excel contains readable source/record/date columns without internal source IDs, and the dashboard PDF is valid. DLW and Activate+ exports remain healthy. Application counts stayed at 2 staff, 5 records and 0 actions. The local database has no actions; populated saves and native-workflow cases were exercised only in disposable test databases or isolated browser fixtures. No migration, fixture reload, remote repository write or deployment was performed. The existing main-bundle size advisory remains.
