# Reporting and operations audit — 29 September 2026

This is a read-only review of the current local source. It covers dashboard loading and refresh, exports, error handling, QA draft/report separation, staff archiving, and hosting/authentication configuration. It does not certify the deployed application, production database, network perimeter, backup restoration, or production performance. No application code, database state, settings, or permissions were changed by this review.

The application targets .NET 10 (`apps/api/src/TLQS.Api/TLQS.Api.csproj:3`). The ASP.NET Core skill and relevant pipeline guidance were consulted. Findings below are based on the source inspected now; earlier runtime reports were not treated as current verification.

## Controls that are present

- QA drafts are separated from recent submissions in the UI (`apps/web/src/routes/QaHub.tsx:735`, `:788`–791). QA export selection explicitly requires submitted, unremoved evidence and applies dashboard-visible team scopes (`Data/QaReviewDataStore.cs:930`–940); dashboard aggregation also uses submitted-only scope (`:1230`). This is a source review, not a new execution of every QA permission combination.
- Dashboard input filtering and export scoping exclude drafts (`Dashboard.tsx:312`–316; `Data/DashboardExportDataStore.cs:216`). Existing test source covers draft exclusion and combined filters in `tests/access-control/DashboardExportScopeTests.cs:77` and `:87`; these tests were inspected, not rerun by this sub-review.
- PDF endpoints request dashboard sections without raw workbook entries (`V1/PlatformOperationsEndpoints.cs:419`). Excel retains form-shaped entry data. Report-menu text explains that the detail-table search does not restrict exports (`ExportButtons.tsx:62`).
- Exports resolve the current user, check module permission, pass that user through data retrieval, and write an export audit record (`V1/PlatformOperationsEndpoints.cs:385`–394 and `:414`–423). This supports the architecture but does not replace testing each real role.
- Archiving prevents self-archive and protects the last active Admin; it records an audit and invalidates roles/scopes. Restore deliberately leaves access disabled (`Data/StaffArchiveDataStore.cs:16`, `:67`–85, `:105`–117). A deliberate reactivation workflow is safer than silently restoring old access.
- Development authentication is gated by both Development environment and explicit configuration; non-development Entra startup requires tenant/audience (`Program.cs:128`–165). HTTPS/HSTS are enabled outside Development (`:225`–228). These are source controls, not production configuration verification.
