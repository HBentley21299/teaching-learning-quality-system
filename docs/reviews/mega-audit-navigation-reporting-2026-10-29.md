# Navigation, people and reporting audit — 29 October 2026

This is a fresh source review of the current shell, people surfaces, reporting and transfer boundaries during the larger administration/versioning change. Earlier review documents are background, not evidence of new execution. No user account, application record, permission, import, configuration or production database was changed by this pass.

## New findings and changes

1. **Reporting-only roles were offered an export they could not use.** Dashboard showed PDF/Excel whenever its data was ready, although the non-UCO export endpoint requires `exports.create`. The control now requires that grant. Reading Form data continues to use its separate reporting permission; UCO continues to use its explicit `canExport` capability.
2. **QA filters could temporarily display the previous cohort.** QA summary state was not associated with faculty/team scope. The new selected filter could render with the previous totals before effects ran, and a superseded request could finish in that interval. Dashboard state now carries its request scope; both the render and async result verify it. The previous totals disappear synchronously, with the contextual loader shown until the current summary arrives.
3. **The navigation toggle used a generic panel glyph.** It now uses the existing light/dark i-Elevate logo and retains explicit Expand/Collapse naming, expanded state, controls relationship and the existing preference action. Desktop placement and mobile menu behavior remain unchanged.
4. **Saved form display names needed to follow their actual version.** Generic answer exports and both UCO report selections now use the saved version's `display_name`, falling back to the parent template name. The corresponding record-list/detail changes in `SqlFoundationDataStore` were passed to the root owner. These queries depend on the new version-metadata migration supplied by that work.
5. **LIV Word export had a similar role-affordance gap.** The API requires the corresponding LIV submit/manage capability or global reporting. The workflow reviewer added the matching optional Word-control gate to LIV; the final `LivVisits` call site and workspace default were re-read. This audit did not weaken the endpoint policy.
6. **Clearing a form description restored older template text.** The shared blank-to-NULL conversion made an intentional blank indistinguishable from legacy metadata. The backend owner now uses the presence of version-specific naming to distinguish initialized metadata, retaining a cleared description through read, publish and copy. A new isolated database regression exercises that path while checking that the historical version keeps its original description.
7. **Multiple-choice control payloads did not match the new server rule.** Both generic form controls and Work Scrutiny serialized additional multiple-choice/checklist answers using `|`; new custom-answer validation required a JSON array. Even selecting one choice could reject a draft or submission. The workflow owner corrected custom-field serialization and parsing while retaining existing CPD formats and option text containing a literal `|`. A subsequent root review found that Work Scrutiny's earlier Application-layer validator also split every answer on `|`. This reviewer corrected that layer for `custom_*` JSON choices, preserving legacy behavior. Domain and actual API-validator tests prove both layers accept configured string arrays and optional `[]`, preserve literal `|`, reject malformed/unknown/repeated choices, and leave required-empty rejection to the shared validator. Four-process export regressions explicitly preserve that option text in both native and Excel output.
8. **The existing Work Scrutiny setup editor bypassed the new editor's concurrency protection.** Its structure endpoint replaced fields without changing the version row or accepting an expected token. The backend owner added the shared parent lock, version metadata/token update and required token check. The administration owner aligned the existing client, including loading the new target's token when copying a template. An isolated SQL regression now proves missing tokens cannot write, both stale directions reject without overwriting, and simultaneous same-token legacy/new writes have exactly one winner with complete fields and matching metadata.
9. **Environment section edits were ignored by the consumer.** The existing consumer forced the room title, substituted live pillar names and used pillar order even when the new editor saved different section titles/order. The workflow owner updated the consumer to honor saved version titles/order while retaining pillar imagery and descriptions. The final consumer functions were re-read; this reviewer made no production edits there.
10. **The existing setup route and Work Scrutiny allocation checks needed readable HTTP errors.** The original structure route is mapped outside the new version route group, so the new group's concurrency filter did not cover it. The root owner extended the API filter to return 409 for the shared form-template path. The new Work Scrutiny allocation helper also translates its controlled SQL 51000 rule failures into the existing readable 400 workflow response. Both changes were re-read after landing; the isolated datastore tests exercise concurrency rejection, rather than claiming HTTP integration coverage.
11. **Work Scrutiny drafts needed safe core-field preparation across both editors.** Blank creation, version copying and older-draft saves now prepare the course-level and delivery-area questions. Both publish routes reject an unprepared older draft until it is saved and reviewed. This reviewer fixed the replacement queries so archived sections and inactive/archived field rows survive until preparation revives them, retaining their identities and configuration. A shared contract protects core section/type/requirement/options/presence in both save routes without imposing new custom-key restrictions on existing templates. Both save routes preserve protected lookup bindings, validation and complete configuration JSON. Additional `custom_*` questions remain editable even inside reserved Work Scrutiny sections. All preparation targets unused drafts; published definitions and saved answers remain intact.

## Future form changes and reporting

The generic export query follows each saved submission's version, sections and field identities; it does not rebuild old records using the newest live form. New/retired fields therefore remain distinct and old entries retain blanks for questions they never contained. Nine supported additional-field types are represented by the saved answer projection: short/long text, number, date, Yes/No/Partial, single/multiple choice, checklist and rubric.

Environment reporting already starts with the generic response builder before adding Pillar Ratings. It does not need a second custom-answer query. The new four-process regression feeds saved custom fields through flattening, business projection, native register projection and real XLSX generation, while retaining existing linked detail rows. Numeric/date column types, historical blanks and multiline/multiple answers are checked.

Stable question identity deliberately spans versions when the question keeps the same technical key. The existing definition builder retains version/wording history; current business headings use one readable identity and do not create a new column just because its wording was renamed. Administrators should create a new custom key for a semantically different question. Changing an existing core response type, required rule, lookup/configuration or managed choices is protected by the new editor's rules.

Additional generic questions appear in Form data and Excel. Arbitrary custom answers do not automatically become new summary measures, thresholds or chart series. Process registration, denominator definitions, specialty detail-sheet allowlists and domain scoring remain explicit code contracts. Typed ELI/LIV/probation/coaching structures continue to require their dedicated workflow support; they were not advertised as arbitrary form builders.

CPD CSV preparation already refuses a published form with additional required questions that its fixed import columns cannot answer. Optional additional answers stay blank. This consequence was reported to the form-editor owner for CPD guidance; no silent bypass or speculative dynamic CSV schema was introduced.
