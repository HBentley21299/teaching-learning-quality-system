# Form logic, usability and permissions review

Review date: 29 September 2026. Scope: source-backed review of every operational form family and its relevant configuration screens. Recommendations below are proposals: this work does not change form questions, required fields, scoring or submission behaviour. The separate dashboard/export and mandatory CPD changes implement the explicitly requested exceptions.

## Evidence and limits

Inspected `apps/web/src/routes/ModuleWorkspace.tsx`, `ElevatePractice.tsx`, `LivVisits.tsx`, `CoachingMentoring.tsx`, `ProbationObservations.tsx`, `UcoTlaReviews.tsx`, `QaHub.tsx`, `ActionsView.tsx`, `FormEditor.tsx`, `FormBuilder.tsx`, `AdminStaffDetails.tsx`, `AdminCentre.tsx`, `apps/web/src/components/WorkScrutinyCreateForm.tsx`, `FirstTimeOnboarding.tsx`, `apps/web/src/features/StaffProfilePanel.tsx`, the form/QA migrations, permission endpoints and SQL role resolution. QA activities and question wording are editable; seeded wording is evidence of the shipped configuration, not proof of the live catalogue. Live read-only API inventory found 49 published templates: 46 Work Scrutiny allocations, one Learning Walk and two CPD templates, plus one archived Work Scrutiny template. The QA catalogue contains 105 current questions across eight activities; all 105 question texts were reviewed. Full template-definition enumeration encountered a SQL timeout on one Work Scrutiny template and 25–30 second reads on others. The definition query was simplified without changing fields; the subsequent restart and runtime retest passed as described below. Read-only SQL verification subsequently confirmed all 46 Work Scrutiny variants have eight sections, 34 active fields and 15 rubric statements. For each section/field key, the section title, question wording, type, required flag, help text and configuration hash are identical across all 46 variants, so the shared recommendations cover every current variant. The revised form-definition SQL returned all 34 fields for the previously failing template in 240 ms (including sqlcmd startup); Endpoint-level retest after restart passed for all 50 published templates, including all 46 Work Scrutiny variants (34 fields each), with no failed reads. The broader database inventory also includes the Elevate Environments and UCO TLA templates alongside the API-listed templates.

## QA Hub forms: individual activity review

The seven shipped QA activities and the current additional Inclusion Learning Walks activity share the evidence editor: select scope and delivery area, respond to snapshotted criteria, autosave draft, submit and retain revisions. Drafts should remain outside reporting. 'Not seen' means insufficient evidence; 'Not applicable' means irrelevant; neither belongs in rated percentages. Configurable labels must not change those stored meanings.

| QA activity | Recommendation |
| --- | --- |
| Lesson Visit | Group by configured theme/week, keep relevant criteria selected for the review, and give a clear observed-evidence comment prompt. Avoid interpreting a short visit as evidence for an entire curriculum. |
| Digital Learning Walk | Show course-space context prominently and group curriculum information, resources and assessment checks. Clarify sampling guidance before activating any draft criteria with unresolved notes. |
| Work Scrutiny | The three live criteria cover effective VIA, actionable VIA feedback, and WWW/EBI. Expand these abbreviations in guidance and explain what sufficient evidence looks like. This is much narrower than standalone Work Scrutiny; label that distinction so users choose the right route and do not duplicate submissions. |
| Walk Around | The four criteria cover punctual start, welcome, register accuracy and environment. Keep this short operational check distinct from a full lesson judgement, and offer Not seen where a visit occurs after the start of the session. |
| Inclusion Learning Walks | Four current criteria are explicitly marked [Training] with the theme Fictional inclusion training. Do not treat this as a production question set without owner review. The topics (accessible resources, adjustments, participation, effective support) form a coherent set; preserve equal ambition rather than grading disability or learner need. |
| Desk Review | Keep Not applicable available where records genuinely do not apply; use Not seen for records absent from the sample. Use grouped document/data themes and optional source references. |
| Stop and Ask | The live 22 criteria repeat six questions across Week 1 and Week 2. When both sets are selected, explain whether separate samples are intended and avoid accidentally collecting the same discussion twice. Keep the interaction short; group only relevant learner questions. Preserve learner anonymity and explain that the recorded outcome is the reviewer's judgement of responses. |
| Student Voice | The live 25 criteria repeat twelve questions across Week 1 and Week 2. Make the intended sampling window visible and avoid interpreting repeated prompts as distinct learner participation. Group the longer discussion into manageable themes. Clarify whether a submission represents one learner or a group before interpreting submission counts as participation counts. |

QA review setup itself is logically separate from evidence collection: review details, question sets, faculty/team allocations, selected activities and question preview. Keep all-teams auto-selection and visible deselection. A published review can expand scope but must retain its snapshotted questions. Recommend a compact pre-publication count of faculties, teams, activities and criteria, plus a deliberate publish action; do not conflate saving setup with opening evidence collection.

## Form configuration screens

Form Editor should continue to be the single entry point for forms and the lists used within them. Keep wording/layout editing, configured choices, rubric wording, access whitelist and version publication together as distinct subsections. Preserve stable field/question keys and historical snapshots when labels change. Work Scrutiny's team-specific published-template requirement needs a clear allocation summary. QA rubric configuration should explain neutral code behaviour separately from label editing. The existing builder's field-type/required-state operations change form behaviour and have deliberately not been altered in this UI review.

## Permission model: audit and implemented improvements

The prior role panel displayed raw capability chips and immediate add/remove actions by role. It described the highest-ranked role as effective, although capabilities are additive. This obscured three separate concepts: job category, capability tier and organisation scope.

Implemented:

- Staff-first access allocation with tier checkboxes, explicit Save/Discard, combined capability preview, searchable people, visible job category and current scopes.
- Organisation-managed assignments and own administrator access remain protected; at least one tier must remain. Existing backend last-admin protections still apply.
- Collapsible, grouped capability catalogue with understandable names and stable permission keys for support/debugging.
- Genuine custom permission-tier creation and editing through authenticated backend endpoints. New tiers start with no capabilities, have no academic/leadership meaning and do not create scope assignments.
- Only capabilities the acting administrator holds can be placed in custom tiers. `cpd.mandatory_log` cannot be granted through custom tiers. System tiers are not editable through this route.
- Existing custom-tier edits use a row-version conflict check and a transaction; changes are audited. Editing a tier explicitly warns that all allocated users are affected.
- Clear guidance that a staff category does not determine access, scopes are managed separately, and broad report capabilities can extend visibility beyond assigned units.
- Unsaved permission work participates in the Admin Centre navigation guard; browser unload also warns.

Verified in source: ReplaceUserRolesAsync resolves any active database role key, so custom keys are allocatable. GetPermissionKeysAsync unions DISTINCT capabilities across active assignments without filtering by role precedence. GetAccessScopesAsync loads scope independently. New custom tiers have precedence 0; role-rank-based action-owner eligibility (Programme Leader and above) deliberately does not treat them as academic leaders. Custom roles are capability bundles, not a substitute for explicit workflow relationships. Validation still depends on programme-leader/manager relationships; assigning a capability alone does not appoint a Director, Head of Faculty or Programme Leader. Per-form QA whitelists remain a separate completion/edit restriction. No existing user's roles, categories, scopes or leadership assignments were migrated by these UI/code changes.

Further recommendation: an 'Explain this person's access' endpoint should combine role grants, direct overrides, hierarchy-derived scope, explicit record assignments and QA whitelist decisions. The current preview shows role-derived capabilities, not a guarantee that a particular record is accessible. An access simulator would require server-side decision tracing and should not be faked from client checkboxes.
